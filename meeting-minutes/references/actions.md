# 行动项提取规则

行动项是纪要里唯一会被逐条追责的内容，也是最容易出错的内容。上游 action tracking 的最佳实践＋内网的"不编造"红线，共同构成本规则。

## 四要素（缺一不可，缺就标"待确认"）

| 要素 | 要求 | 反例 |
| --- | --- | --- |
| 事项 | 具体可验收："9月20日前将修订稿发各部门征求意见"，不是"跟进修订工作" | "加强对接" |
| 责任人 | 唯一自然人或明确科室（责任人只能有一个，协办可以多个） | "相关部门" |
| 截止日期 | 具体到日："9月20日前"，不是"尽快""下周内尽量" | "ASAP" |
| 依赖 | 依赖的前置事项或外部输入，注明 | 隐含依赖导致延期 |

## 从讨论到行动项的判断

- **算行动项**：主持人总结的"××负责、××前完成"；与会各方无异议的分工；"下次会前把××报来"；
- **不算行动项**：个人观点、讨论中未被采纳的建议、纯背景陈述；
- **模糊表述**（"这事抓紧办"）：未指明责任人和日期时，写进待确认行动项并把原话记入备注，不替会议解释；
- **口头指定**（"小李你牵头"）：转写中的人名要与参会名单核对，对不上号的标"待确认（转写音'xiǎolǐ'，待核）"。

## 类型区分（沿用上游四分法）

- 本部门动作（纪要主责单位要做的事）；
- 其他部门动作（需转交、抄送的）；
- 外部动作（需企业、上级、外单位配合的）；
- 需另行安排的会议（写进"其他事项"）。

类型影响分发对象：台账"备注"列注明"需转交××""需外部配合"。

## 提交脚本的格式

```json
[
  {"事项": "9月20日前将修订稿发各部门征求意见",
   "责任人": "王五", "协办": "法规科",
   "截止日期": "2026-09-20", "优先级": "高"},
  {"事项": "核实管线走向的会议结论",
   "责任人": "", "截止日期": "", "优先级": "中"}
]
```

第二条生成后会标"待确认"——这是特性不是缺陷：宁可会后多问一句，不能让台账带着假责任人跑。

## 跟踪节奏（上游实践的本地化）

| 优先级 | 核对频率 | 逾期处理 |
| --- | --- | --- |
| 高 | 每日 | 提示责任人和分管领导，下次会议列出 |
| 中 | 每周例会 | 周例会点名 |
| 低 | 下次同主题会议 | 会议材料附上 |
