# 材料起草

目标：交付结构符合材料类型、事实可溯源、能直接进入审稿环节的初稿，并用待补清单把"还缺什么"一次说清，减少用户来回修改的轮次。只在内网环境工作：读用户粘贴的内容和本地文件，不访问外网，不调用外部检索。

## 唯一硬约束：事实必须可溯源

公文材料可能被直接上报或印发，编造的数字、文号、人名一旦留存就是事故。所以本技能只有一条硬约束：**初稿中每个事实性内容都必须来自用户提供的素材；素材里没有的，用占位符标出并进待补清单，不估计，不"合理虚构"。** 固定句式（如"现将有关情况报告如下"）不是事实，正常使用。占位符与待补清单的格式见 [待补事实规范](references/fact-gap.md)。

## 流程

### 阶段一：明确任务与收集素材

先判断材料类型（见文末类型一览），再从用户消息和附件里收集六要素：

| 要素 | 缺了怎么办 |
| --- | --- |
| 材料类型 | 按素材和用户说法推断，交付前向用户确认一句 |
| 读者与用途 | 必须确认：给谁看、上报/宣讲/存档/决策哪一种 |
| 时间范围 | 总结、计划、汇报类必须明确 |
| 素材（要点、数据、历史材料、上级文件） | 决定能否开工 |
| 篇幅 | 未说明时用所选类型的默认篇幅，并告知用户 |
| 模板或格式要求 | 有则遵从；用户给出本地文件路径时读取 |

最小可开工条件是"类型 + 读者 + 素材"。满足就先出骨架，其余要素随骨架确认一次补问：一次问齐、不超过 3 个问题、不逐条打断。用户只说"写个总结"时，按"类型→读者与用途→时间范围和篇幅"的顺序问。

收集素材时告诉用户：素材怎么给都行——粘贴、给文件路径、想到哪说到哪都可以，不用先整理；说明等素材倒完会集中提问，让用户放心先倾倒。判断素材够不够的标准：还能问出基础情况说明不够，只能问到细节和取舍了说明够开工。宿主提供知识库、文件检索等能力时可直接收集，没有就请用户提供。

快速模式：用户首条消息已给全类型、素材和篇幅，或明确说"直接写、不用问了"时，跳过提问直接进入阶段二，交付时注明依据了哪些假设。

结构化模式（长材料、上报件、领导讲话稿的默认）：开工前用两三句告知流程——先出骨架确认，再逐段起草，交付附待补清单——让用户对节奏有预期。用户想跳过任何环节、直接要成文时随他：流程是为出稿服务的，不是反过来。

### 阶段二：定结构、逐段起草

1. 读取所选类型的规则文件 `references/types/<type>.md`（每种材料只读自己那一份）。骨架可用脚本直接生成：
   ```bash
   python "<SKILL>/scripts/facts.py" new work-summary --title "××单位2025年工作总结" -o draft.md
   ```
   也可直接手写骨架。用户提供了单位模板时以用户模板为准。上报、决策、领导讲话类重要材料先把骨架给用户确认再展开全文——结构返工的代价是整篇；日常短材料结构有把握时直接写。
2. 起草顺序：从素材最实的主体部分写起（如总结的"主要工作"、请示的"请示事项"），开头总述、结尾表态这类概括性段落最后写——概括要覆盖全文，先写必返工。用户指定顺序时随用户。
3. 逐段起草。动笔前把素材重扫一遍，用户提过但容易被漏掉的信息先捡出来；有素材的事实写实，没有的写占位符后继续往下写，不逐个追问——占位符本身就是提问，集中收集比逐条打断快。观点性内容（板块小标题、提纲要点、经验做法标题）先给 3-5 个候选让用户挑再展开：小标题定调，后文都跟着走。
4. 处理反馈：只改点名的段落，不整篇重写重贴；用户在反馈里的每次取舍（删了什么、留了什么）记下来用于后面段落。用户自己改稿后发回来时，把改动当作偏好信号，后续段落照此风格写。
5. 全程遵守 [共同写作规则](references/rules.md)：语体、时间与数字写法、称谓一致、套话控制、提问方式。

### 阶段三：自查、扫描、交付

1. 对照类型规则文件里的"事实核验点"自查：关键时间、数字、主体是否齐全，口径是否前后一致，是否踩了该类型的禁忌。然后通读全文一遍，专查段落衔接、前后重复、相互矛盾和"删掉不影响信息量"的句子。用户连续一轮反馈只剩措辞级意见时，主动问哪些段落可以删——公文常见毛病是越改越长。
2. 用脚本扫描占位符并生成待补清单，保证一个不漏：
   ```bash
   python "<SKILL>/scripts/facts.py" scan draft.md --out 待补事实清单.md
   ```
   无 Python 或在聊天内交付短文时，按 [待补事实规范](references/fact-gap.md) 的人工格式清点，并逐段核对无遗漏。
3. 上报、决策、领导讲话类材料做一次读者自查，方法见 [读者测试](references/reader-test.md)；宿主支持子代理时，可用新上下文子代理扮演读者。
4. 交付初稿和待补清单两部分，并请用户通读确认——报送、签发的责任在用户，本技能对"事实可溯源、结构合规"负责，不替用户把关是否报送。收尾用一句话衔接流水线：内容层面建议先过材料审稿，定稿前用文字校对技能查错别字和标点。

## 交付格式

约 800 字以内且用户在聊天里要的，直接在回复中给初稿和待补清单；其余写文件：`draft.md`（初稿）和 `待补事实清单.md`，并给出路径。待补清单固定栏目：

```markdown
# 待补事实清单

| # | 位置 | 类别 | 待补内容 | 建议来源 |
| --- | --- | --- | --- | --- |
| 1 | 一、主要工作（一） | 数字 | 全年培训期数、参训人次 | 培训台账 |
```

用户补齐素材回填后、宣布"定稿"前，运行 `python "<SKILL>/scripts/facts.py" check draft.md`；有残留占位就明确提示，不带占位符的稿子才叫"定稿"，否则一律称"初稿"。

## 材料类型一览

| 类型 | type 值 | 常见说法 |
| --- | --- | --- |
| 工作总结 | work-summary | 年终总结、半年总结、专项工作总结 |
| 工作计划 | work-plan | 年度计划、工作安排、工作要点 |
| 情况汇报 | situation-report | 情况报告、汇报材料、进展报告 |
| 请示 | request | 请示件、报请批准事项 |
| 通知 | notice | 发通知、工作提示 |
| 会议材料 | meeting-material | 议题材料、会议汇报材料、会议发言材料 |
| 述职材料 | duty-report | 述职报告、个人述职 |
| 经验交流材料 | experience-exchange | 交流材料、典型经验做法 |
| 讲话稿/提纲 | speech | 领导讲话、发言提纲、致辞 |

用户要的材料不在表中时，选结构最接近的类型作参考，向用户说明并确认结构后再写。
